1. Pendahuluan
1.1 Tujuan Dokumen
Dokumen ini menjelaskan rancangan teknis dan arsitektur perangkat lunak sistem GEMATI (Gerakan Mangunharjo Anti Stunting), mencakup pemilihan teknologi, struktur basis data, serta diagram desain (Use Case, Activity, Sequence, Class, Deployment, dan Data Flow Diagram). Dokumen ini menjadi acuan teknis bagi tim pengembang dalam membangun sistem sesuai kebutuhan yang telah didefinisikan pada PRD dan SRS.
1.2 Lingkup Dokumen
TDD ini melengkapi Product Requirements Document (PRD) yang memuat tujuan bisnis dan kebutuhan pengguna, serta Software Requirements Specification (SRS) yang memuat kebutuhan fungsional dan non-fungsional, dengan detail implementasi: bagaimana sistem dibangun, struktur datanya, dan bagaimana komponen-komponennya saling berinteraksi.
1.3 Referensi
Product Requirements Document (PRD) GEMATI.
Software Requirements Specification (SRS) GEMATI — REQ-F-01 s.d. REQ-F-17, REQ-NF-01 s.d. REQ-NF-12.
2. Arsitektur Sistem
GEMATI menggunakan arsitektur client-server dengan API terpisah (decoupled architecture), yang memisahkan secara jelas antara antarmuka pengguna (frontend) dan logika bisnis (backend):
[ Next.js / React Frontend ]  ⇄  (REST API · HTTPS/JSON)  ⇄  [ Django Backend ]  ⇄  [ PostgreSQL Database (lokal) ]
Frontend (Next.js/React) menangani seluruh tampilan antarmuka pengguna (dasbor, formulir input, portal edukasi publik) dan berkomunikasi ke backend melalui REST API.
Backend (Django + Django REST Framework) menangani business logic: autentikasi & otorisasi berbasis role, kalkulasi Z-Score otomatis, deteksi early warning, dan endpoint API untuk seluruh operasi CRUD.
Database (PostgreSQL, di-hosting secara lokal pada lingkungan pengembangan) menyimpan seluruh data persisten: pengguna, balita, data antropometri, riwayat Z-Score, dan log intervensi PMT.
Pemisahan frontend dan backend ini memudahkan pengembangan paralel oleh tim sesuai pembagian peran proyek, dan memungkinkan API yang sama dikonsumsi oleh klien lain di masa depan (misalnya aplikasi mobile) tanpa mengubah backend.

Catatan deployment: Pada tahap pengembangan KKN ini, sistem dijalankan dan diuji di lingkungan lokal (local development server). Strategi hosting/deployment ke server produksi (VPS, cloud, atau infrastruktur kampus) akan ditentukan kemudian dan didokumentasikan sebagai pembaruan pada bagian ini. Spesifikasi minimal server mengacu pada SRS §2.4 (RAM minimal 1 GB, penyimpanan 10 GB) sebagai baseline ketika deployment sudah direncanakan.
3.1 Struktur Direktori Proyek
Proyek GEMATI menggunakan struktur monorepo, yaitu frontend dan backend disimpan dalam satu repository yang sama namun pada folder terpisah. Pendekatan ini dipilih karena ukuran tim yang kecil (dua anggota) sehingga memudahkan koordinasi dan menjaga keselarasan versi antara frontend dan backend dalam satu riwayat commit.
Pada sisi backend, struktur aplikasi Django dipecah per modul/fitur (app-based), mengikuti pengelompokan kebutuhan fungsional yang telah didefinisikan pada SRS (Autentikasi, Data Posyandu, Data Balita, Input Antropometri, Kalkulasi Z-Score, Peringatan Dini, Log PMT, dan Pelaporan).

4. Entity Relationship Diagram (ERD)
ERD berikut menggambarkan struktur basis data PostgreSQL yang digunakan oleh sistem GEMATI, mencakup entitas pengguna, posyandu, balita, data antropometri, hasil kalkulasi Z-Score, peringatan dini, dan log intervensi PMT.
Catatan desain: relasi DATA_ANTROPOMETRI ke ZSCORE_LOG bersifat satu-ke-banyak (1-to-many) — satu baris input antropometri (berat badan & tinggi badan) menghasilkan tiga baris pada ZSCORE_LOG, masing-masing untuk indikator BB/U (berat badan menurut umur), TB/U (tinggi badan menurut umur), dan BB/TB (berat badan menurut tinggi badan).

6. Activity Diagram
Activity Diagram berikut menggambarkan alur kerja (workflow) sistem GEMATI untuk masing-masing kelompok aktor, mencakup urutan aktivitas, titik percabangan keputusan, dan perulangan proses.
6.1 Activity Diagram — Kader Posyandu
Diagram ini menggambarkan alur kerja Kader Posyandu mulai dari login, input data antropometri, hingga proses otomatis kalkulasi status gizi (UC-03) dan analisis risiko stunting (UC-04) yang dilanjutkan dengan penyimpanan data. Apabila hasil koreksi data dinyatakan tidak valid, alur diarahkan ke proses verifikasi/koreksi data balita (UC-08); apabila valid, Kader dapat melihat riwayat pertumbuhan balita (UC-05).
6.2 Activity Diagram — Bidan Desa / Perangkat Desa
Diagram ini menggambarkan alur kerja Bidan Desa/Perangkat Desa mulai dari login, melihat dashboard pemantauan, hingga analisis risiko stunting yang menentukan apakah diperlukan intervensi PMT (UC-09) atau tidak. Bidan juga memiliki akses untuk mengelola data posyandu (UC-07), mengelola akun kader (UC-10), dan mengekspor laporan (UC-11).
6.3 Activity Diagram — Masyarakat
Diagram ini menggambarkan alur akses publik tanpa login, yaitu mengakses portal edukasi (UC-12), melihat statistik stunting desa (UC-13), dan membaca materi edukasi seputar stunting, gizi, dan sanitasi.
7. Sequence Diagram
Sequence Diagram berikut menggambarkan interaksi antar objek (boundary, control, entity, dan database) dalam menjalankan skenario utama sistem GEMATI, mengikuti pola arsitektur Boundary-Control-Entity (BCE).
7.1 SD-01 — Login
Diagram ini menggambarkan proses autentikasi pengguna (Kader atau Bidan Desa), mulai dari akses halaman login, validasi kredensial oleh Auth Controller terhadap data pada tabel USER, hingga dua kemungkinan hasil: login berhasil (diarahkan ke dashboard) atau login gagal (ditampilkan pesan kesalahan).
7.2 SD-02 — Input Data Antropometri, Hitung Status Gizi, dan Analisis Risiko Stunting
Diagram ini menggambarkan alur Kader Posyandu menginput data antropometri balita, yang kemudian diproses oleh Antropometri Controller: validasi data, penyimpanan ke basis data, kalkulasi status gizi (BB/U, TB/U, BB/TB), dan analisis risiko stunting. Hasil status gizi dan risiko stunting ditampilkan kembali kepada Kader. Apabila data tidak valid, sistem menampilkan pesan kesalahan/validasi tanpa menyimpan data.
7.3 SD-03 — Dashboard Pemantauan, Verifikasi Data, dan Catat Intervensi PMT
Diagram ini menggambarkan alur Bidan Desa/Perangkat Desa membuka dashboard pemantauan yang menampilkan data balita beserta hasil analisis risiko. Terdapat dua titik percabangan: pertama, apakah data balita perlu dikoreksi atau sudah benar; kedua, apakah balita berisiko stunting sehingga memerlukan pencatatan intervensi PMT (UC-09) atau tidak.
7.4 SD-04 — Portal Edukasi dan Statistik Stunting
Diagram ini menggambarkan alur Masyarakat/pengunjung mengakses portal edukasi tanpa memerlukan login. Pengunjung dapat melihat konten edukasi umum, dan secara opsional memilih menu statistik stunting desa untuk melihat data agregat secara publik.
